# Buddy — 全流程交付技能

当任务需要从模糊需求推进到具体交付时，使用此技能。

## 触发条件

- 用户说 `/buddy` 或 "帮我做"、"全流程"、"从头到尾"
- 用户给出一个需要多阶段推进的任务
- 用户指定某个阶段（如"帮我review"、"帮我写测试"）

## 工作流

### 阶段 0：理解意图

- 判断用户需要全流程还是单阶段
- 如果是单阶段，直接跳到对应阶段
- 如果是全流程，按顺序推进

### 阶段 1：需求分析（Requirements）

委派给 `agents/requirement-analyst.md` 的职责：

- 提取目标、成功标准、约束条件、影响范围
- 缺失细节时做最小安全假设并记录
- 输出：需求摘要文档

### 阶段 2：架构设计（Architecture）

委派给 `agents/architect.md` 的职责：

- 分析现有代码结构和依赖
- 确定最小可行变更集
- 识别风险依赖和跨模块影响
- 输出：设计方案（含方案选择理由）

### 阶段 3：编码实现（Coding）

委派给 `agents/coder.md` 的职责：

- 遵循项目现有编码规范和代码风格
- 增量、可逆的修改优先于大范围重构
- 保持现有代码风格一致性
- 输出：代码变更

### 阶段 4：代码审查（Review）

委派给 `agents/reviewer.md` 的职责：

- 检查代码质量、安全性、一致性
- 验证是否符合项目规范
- 标注风险点和改进建议
- 输出：审查报告

### 阶段 5：测试验证（Testing）

委派给 `agents/tester.md` 的职责：

- 先跑最窄有效检查，再扩大覆盖面
- 验证变更不破坏既有功能
- 输出：测试结果和覆盖报告

### 阶段 6：部署发布（Deployment）

委派给 `agents/deployer.md` 的职责：

- 构建打包验证
- 生成部署清单和回滚方案
- 输出：部署文档和交付说明

## 交付输出

最终响应须覆盖：

1. **需求摘要** — 目标、范围、约束
2. **设计方案** — 方案选择及理由
3. **代码变更** — 改了什么、为什么
4. **审查结论** — 风险点和改进项
5. **测试证据** — 执行结果
6. **部署说明** — 如何运行、回滚方案

大型任务使用 [references/delivery-template.md](references/delivery-template.md) 模板。

## 记忆管理

Buddy 在每次对话中必须执行以下记忆操作，确保跨对话的连续性。

记忆存储路径：`/Users/yuan/.claude/projects/-Users-yuan-villa-party-booking/memory/`
记忆索引文件：`/Users/yuan/.claude/projects/-Users-yuan-villa-party-booking/memory/MEMORY.md`

### 对话开始时：读取记忆

- 读取 `MEMORY.md` 索引文件，了解已有记忆
- 根据当前任务上下文，读取相关的记忆文件
- 将记忆中的信息作为背景参考

### 对话过程中：按需保存

以下情况必须保存记忆：

| 触发条件 | 记忆类型 | 示例 |
|----------|----------|------|
| 了解到用户角色、偏好、技能 | `user` | 用户是全栈开发，熟悉某框架 |
| 用户纠正或确认了工作方式 | `feedback` | 用户偏好一次提交完整 PR |
| 了解到项目背景、目标、约束 | `project` | 项目的核心业务目标和约束 |
| 发现外部资源引用 | `reference` | 接口文档在某个链接 |

### 交付完成时：保存交付记录

每次完成一个需求交付后，保存一条 `project` 类型记忆，包含：
- 需求简述
- 关键设计决策
- 未完成的待办项（如有）
- 日期（使用绝对日期）

文件命名规则：`{type}_{topic}.md`，如 `project_vehicle_module.md`、`user_profile.md`

### 记忆文件格式

```markdown
---
name: {{记忆名称}}
description: {{一行描述，用于判断相关性}}
type: {{user | feedback | project | reference}}
---

{{记忆内容}}
```

### 记忆精简原则

**只保留关键记忆**——能从代码、git 历史、配置文件推导出的信息一律不保存。值得保存的记忆必须满足以下至少一条：
- 影响未来决策的设计理由或约束
- 用户明确表达的偏好或工作方式
- 无法从代码推导的项目背景（如业务动机、外部依赖关系）
- 未完成的待办项或阻塞点

**48 小时记忆优化**——每次对话开始读取记忆时，检查每条记忆的日期：
1. 超过 48 小时的 `project` 类型记忆，评估是否仍有价值：
   - 已完成的交付记录：提炼为一句话摘要，删除详细过程
   - 已过期的约束或计划：直接删除
   - 仍有效的长期决策：保留，更新日期标记为"已审核"
2. `user` 和 `feedback` 类型记忆通常长期有效，仅在发现矛盾或过时时更新
3. `reference` 类型记忆在引用失效时删除
4. 优化后同步更新 `MEMORY.md` 索引，移除已删除记忆的条目

### 其他注意事项

- 保存前检查是否已有相关记忆，优先更新而非新建
- 相对日期必须转换为绝对日期
- 保存后同步更新 `MEMORY.md` 索引

## 原则

- 增量可逆优先于大范围重构
- 保持既有约定，除非任务明确要求重新设计
- 记录执行的命令、关键输出、未验证的缺口
- 如需 Codex 协助，参考 [references/codex-consultation.md](references/codex-consultation.md)
